# pyselector 常駐モード（サーバーモード）設計

`docs/09_agent_mode_plan.md` の「9.3 常駐モード / MCP」を、MCP を使わない形で実装するための設計。

---

## 1. 目的

### 1.1 MCP を使わない

MCP は通信手段の 1 つであって、常駐化の本質ではない。MCP サーバーの利用が制限された環境化を想定し、**MCP に依存しない形**で同じ効果を得る。

方針は「**常駐プロセスを実装の内部に隠し、エージェントから見えるインターフェースは今の CLI のまま変えない**」。エージェントは引き続き次のように打つだけで、内部で高速化される。

```bash
pyselector find --json --window-handle 0x2E20F46 --control-type Button
```

新しいプロトコルもクライアント設定も不要で、常駐していなければ従来どおりその場で実行される。

### 1.2 解決する課題

実測（開発機）による、1 コマンドあたりの固定コスト。

```text
Python インタプリタ起動           0.09 秒
+ pyselector の import            0.19 秒（累計）
+ pywinauto の import             0.54 秒（累計）
────────────────────────────────────────────
find の実処理（227 要素の走査）    0.94 秒
```

`find` の 1.57 秒のうち **約 0.55 秒が固定のプロセス起動コスト**。常駐化で消せるのはここだけで、UI 走査そのもの（0.94 秒）は変わらない。

ただし速度以上に重要なのが **状態の保持** である。現在、要素の参照 ID（`ElementInfo.ref`）はプロセス内でしか有効でないため JSON に出していない。常駐すれば ref をコマンドをまたいで使えるようになり、次が可能になる。

```bash
pyselector find --json --window-handle 0x... --auto-id saveBtn   # → ref: "uia:7f3a2b:42"
pyselector act --ref uia:7f3a2b:42 --click --allow-actions
```

座標も再検索も要らず、`act` の対象が曖昧になる余地が消える。**これが常駐化の主目的**で、速度は副産物と位置づける。

## 2. 全体像

```text
┌─ pyselector serve（常駐、1 ユーザーにつき 1 つ）──────────┐
│  ・pywinauto を import 済み                              │
│  ・Win32Inspector / UiaInspector を保持                  │
│  ・wrapper の参照表（ref → pywinauto wrapper）を保持     │
│  ・単一スレッドで逐次処理（COM の制約）                  │
└──────────────────────────────────────────────────────────┘
        ▲ 名前付きパイプ \\.\pipe\pyselector-<SID>
        │ 要求: {"argv": [...], "cwd": "...", "version": "..."}
        │ 応答: {"stdout": "...", "stderr": "...", "exit_code": 0}
        │
┌─ pyselector find --json ...（毎回起動する薄いクライアント）┐
│  ・pywinauto を import しない（0.19 秒で済む）            │
│  ・応答をそのまま出力し、同じ終了コードで終わる           │
│  ・繋がらなければ従来どおりその場で実行する               │
└───────────────────────────────────────────────────────────┘
```

## 3. なぜ argv をそのまま転送するのか

サーバーに送るのは **コマンドライン引数の配列そのもの**とし、サーバー側は既存の `main()` と同じ経路で実行して標準出力・標準エラー・終了コードを返す。

```json
{
  "protocol": 1,
  "version": "0.2.0",
  "cwd": "D:\\Script\\pyselector",
  "argv": ["find", "--json", "--window-handle", "18943796", "--control-type", "Button"]
}
```

コマンドごとに RPC メソッドを定義する設計にしないのは、**ローカル実行と常駐実行で挙動が分岐する余地をなくす**ため。引数解析・設定読み込み・出力整形をすべて共有すれば、「サーバー経由だけ結果が違う」というバグが構造的に起きない。新しいサブコマンドを足したときにサーバー側の対応を忘れることもない。

`cwd` を送るのは、設定ファイル（`pyselector_config.json`）がカレントディレクトリ基準で読まれるため。サーバーは要求ごとにクライアントの `cwd` で設定を読み直す。これによりサーバーの起動場所は結果に影響しない。

## 4. 通信路

### 4.1 名前付きパイプを選ぶ理由

TCP（127.0.0.1）と比較したうえで、名前付きパイプを採用する。

| 観点 | 名前付きパイプ | TCP (127.0.0.1) |
| --- | --- | --- |
| プラットフォームの作法 | Windows のローカル IPC のネイティブな手段 | クロスプラットフォーム前提の作法 |
| 認証 | **カーネルが SID で強制**。秘密情報を持たない | 共有トークンを自前で実装する必要がある |
| 防御境界 | オブジェクトの ACL | トークンファイルの ACL |
| 発見 | SID から名前が決まる | 状態ファイルでポートを知る必要がある |
| ポート枯渇・衝突 | 起きない | 起きうる |
| ファイアウォール | 無関係 | ループバック限定なら通常は出ないが、バインド先を誤ると出る |
| 実装コスト | オーバーラップド I/O が必要（TCP の約 3 倍） | 標準ライブラリで完結 |
| テスト容易性 | 実パイプは CI で扱いづらい | ポート 0 で本物のソケットを使える |

TCP は実装とテストの面で明確に有利だが、**認証を自前で作ることになる点**を重く見て採用しない。

このサーバーは `act` を許可すればデスクトップを操作でき、常時どのウィンドウの内容も読み取れる。画面には機微な情報が映っていることもある。この能力に対して、名前付きパイプなら認証が構造的に成立する（漏れる秘密情報がなく、トークンの検証漏れというバグが起こりえない）のに対し、TCP ではファイル ACL で守ったトークンが実質的な防御境界になる。カーネル強制の ACL より弱く、間違えやすい。

実装コストとテスト容易性は、4.5 のトランスポート抽象で回収する。

### 4.2 パイプ名と ACL

```text
パイプ名: \\.\pipe\pyselector-<現在のユーザーの SID>
ACL     : D:(A;;GA;;;<SID>)(A;;GA;;;SY)   … 実行ユーザーと SYSTEM のみ
```

SID をパイプ名に含めることで、同一マシンの複数ユーザーが衝突しない。

### 4.3 実装手段

`pywin32`（`win32pipe` / `win32file` / `win32security`）を使う。**pywinauto が既に `pywin32` に依存しているため、追加の依存関係は発生しない。**

### 4.4 プロトコル

メッセージモードのパイプで、1 要求 = 1 メッセージ、1 応答 = 1 メッセージ。UTF-8 の JSON。接続は 1 要求ごとに閉じる。

実測で往復 **0.45 ミリ秒**。通信自体のコストは無視できる。

### 4.5 トランスポート抽象

通信路を差し替え可能にし、サーバーのループ本体から切り離す。

```python
class Transport(Protocol):
    def listen(self) -> None: ...
    def accept(self, timeout: float) -> Connection | None: ...   # timeout でアイドル判定
    def close(self) -> None: ...

class Connection(Protocol):
    def receive(self) -> bytes: ...
    def send(self, payload: bytes) -> None: ...
    def close(self) -> None: ...
```

- **本番で使うのは名前付きパイプ実装のみ**
- テストではループバック TCP 実装を使い、受付ループ・argv 転送・ref 管理・アイドルタイムアウトを**本物のソケット越しに**検証する（ポート 0 でバインドすれば衝突しない）。偽チャネルで済ませるより実態に近い
- パイプ実装そのものは、実パイプを使う結合テスト 1 本で担保する

TCP 実装をテスト専用に留めるのは、本番でポートを開けば 4.1 の認証の議論をやり直すことになるため。将来 MCP-over-HTTP のような要求が出た場合は、この抽象の上に本番用トランスポートとして足せる。

### 4.6 並行性

pywinauto と COM はスレッド安全ではない。**サーバーは単一スレッドで要求を逐次処理する。** パイプインスタンスは複数許可し、処理中に来たクライアントは待たせる。クライアントは `WaitNamedPipe` にタイムアウト（既定 30 秒）を設定し、超えたらローカル実行にフォールバックする。

UI 操作は本質的に直列なので、この制約が実用上の問題になることはない。

## 5. サーバーのライフサイクル

### 5.1 サーバーを起動しなくても使えること（最優先の前提）

**サーバーは必須ではない。** 常駐モードはあくまで最適化であり、次の 3 段階で段階的に選べる。

| 状態 | 利用者が行う操作 | 挙動 |
| --- | --- | --- |
| 既定（設定を書かない） | **なし** | 常駐プロセスは存在しない。現在とまったく同じ動作 |
| `server.enabled: true` | **なし** | 必要になった時点で自動起動し、アイドルで自ら終了する |
| 手動管理したい場合 | `pyselector serve` | `auto_start: false` にして自分で起動・停止する |

「サーバーを起動しないと使えない」状態は作らない。設定を書かない限りクライアントはサーバーを探しにいかず、書いた場合も起動していなければ黙ってローカル実行に落ちる。

さらに 6.2 のとおり、サーバーを経由するのは `--json` 指定時のみである。**オーバーレイをクリックする従来の使い方は、サーバーが動いていても経由しない。**

### 5.2 起動

```bash
pyselector serve                      # フォアグラウンドで起動
pyselector serve --idle-timeout 600   # 無操作 600 秒で自動終了（既定 300）
pyselector serve --allow-actions      # act の実行を許可する（後述）
```

`server.enabled: true` のとき、クライアントは必要に応じてサーバーを自動起動する（`server.auto_start`、既定 `true`）。設定で常駐モードを有効にした時点で常駐を望んでいるのは明らかなので、そこから先で手動起動を要求しない。

自動起動時、**その 1 回目のコマンドはサーバーの準備を待たない。** サーバーをデタッチして起動したうえで、自身はローカル実行で結果を返す。待たせると 1 回目だけ体感が悪化するため。2 回目以降のコマンドが常駐サーバーを使う。

プロセスを自分で管理したい場合は `server.auto_start: false` にする。

### 5.3 状態ファイル

```text
%LOCALAPPDATA%\pyselector\server.json
{"pid": 12345, "pipe": "\\\\.\\pipe\\pyselector-S-1-5-...", "instance_id": "7f3a2b",
 "version": "0.2.0", "started_at": "2026-08-23T12:00:00", "allow_actions": false}
```

接続そのものにこのファイルは不要（パイプ名は SID から決まる）。`--status` / `--stop` と、状態の可視化のために置く。

### 5.4 停止と孤児対策

```bash
pyselector serve --status   # 稼働状況を表示（--json 可）
pyselector serve --stop     # 停止要求を送る
```

孤児プロセスを残さないため、次の 3 つを用意する。

1. **アイドルタイムアウト**（既定 300 秒）。最後の要求から一定時間で自ら終了する
2. `serve --stop` による明示停止
3. 状態ファイルの `pid` が生存しない場合、`--status` は「停止済み」と報告し、古い状態ファイルを掃除する

アイドル判定のため、`ConnectNamedPipe` はオーバーラップド I/O で行い、待機にタイムアウトを設ける。

### 5.5 バージョン不一致

要求にクライアントの版数を含める。サーバーと異なる場合、サーバーは `version_mismatch` を返し、クライアントはローカル実行にフォールバックしたうえで、その旨を標準エラーに出す。`pip install -e .` で更新した後に古いサーバーが結果を返し続ける事故を防ぐ。

## 6. クライアントの動作

### 6.1 `--server` オプション

全コマンド共通で追加する。

```text
--server auto      繋がれば使う。繋がらなければローカル実行（設定で有効化したときの既定）
--server off       常にローカル実行（設定に関わらず）
--server require   サーバーが必須。繋がらなければエラー（終了コード 11）
```

`require` は、ref を確実に使いたいエージェントのためにある。`auto` で黙ってローカルに落ちると ref が返らないため、その判別手段が要る。

### 6.2 `--json` のときだけ使う

`auto` でサーバーを使うのは **`--json` 指定時のみ**とする。理由は 2 つ。

- テキスト出力には進捗ログ（`[INFO] uia: UI要素ツリー取得中... 120件完了`）があり、これは逐次表示されることに意味がある。サーバー経由では応答を一括で返すため、この体験が壊れる
- 常駐モードの利用者はエージェントであり、エージェントは常に `--json` を使う

人がテキスト出力で常駐モードを試したい場合は `--server require` を明示する。

### 6.3 フォールバックの可視化

サーバーを使ったかどうかは、出力から判別できる必要がある。JSON エンベロープに `served` を追加する。

```json
{
  "schema_version": 2,
  "command": "find",
  "status": "success",
  "served": true,
  "...": "既存キーはそのまま"
}
```

## 7. 要素参照（ref）

常駐モードの主目的。

### 7.1 形式

```text
<backend>:<サーバーインスタンスID>:<連番>     例: uia:7f3a2b:42
```

インスタンス ID を含めることで、サーバーを再起動した後に古い ref を使った場合、参照表を引くまでもなく無効と判定できる。

### 7.2 出力する条件

**サーバー経由のときだけ `ref` を出力する。** ローカル実行時は ref がプロセス終了とともに消えるため、出力すると「使えるはず」と誤解させる。

### 7.3 ref を受け取るコマンド

```bash
pyselector inspect --ref uia:7f3a2b:42 --json
pyselector act --ref uia:7f3a2b:42 --click --allow-actions
pyselector find --ref uia:7f3a2b:42 --control-type Button --json   # 探索の起点として
pyselector tree --ref uia:7f3a2b:42 --json
```

`--ref` は `--at` / `--window-handle` / `--window-title` と排他。

### 7.4 失効の扱い

ref が指す wrapper は、画面が変われば無効になる。使用時に軽い生存確認（`is_visible()` 相当）を行い、失敗したら実行せずエラーを返す。

```text
終了コード 9 / code: "stale_ref"
message: "この参照は無効になっています。find で取得し直してください"
```

**特に `act` では、失効した ref で意図しない要素を操作しないことが重要**なので、生存確認に失敗した時点で操作は行わない。

### 7.5 参照表の上限

無制限に貯めるとメモリを圧迫する。LRU で上限を設ける（設定 `server.max_refs`、既定 5000）。追い出された ref は `stale_ref` として扱う。

## 8. セキュリティ

### 8.1 権限は増えない

パイプは実行ユーザーの SID に限定される。**同じユーザーで動く他のプロセスは、パイプに繋がなくても最初から `pyselector` を直接実行できる。** したがって常駐化によって新たにできることは増えない。この点を README に明記する。

### 8.2 `act` の扱い

`act` の既存の二重ゲート（設定の `act.allow_actions` と `--allow-actions`）は、サーバー側でクライアントの `cwd` の設定を読んで評価する。ローカル実行と同じ判定になる。

そのうえで、**サーバーは既定で `act` を拒否する**。実行を許すには起動時に明示する。

```bash
pyselector serve --allow-actions
```

一発で終わるコマンドと違い、常駐プロセスは「UI を操作できる口が開き続けている」状態になる。リスクの質が違うため、常駐させること自体への同意を別に取る。拒否時は終了コード 7（`action_not_allowed`）で、理由を明示する。

### 8.3 サーバーで実行しないコマンド

```text
serve            … 再帰を防ぐ
install-skills   … ファイルを書き出す。クライアント側で実行すれば足りる
```

許可リスト方式とし、`inspect` / `tree` / `windows` / `find` / `act` / `diff` / `version` のみサーバーで実行する。想定外のコマンドはローカルにフォールバックする。

## 9. 設定

```json
{
  "server": {
    "enabled": false,
    "auto_start": true,
    "idle_timeout": 300,
    "max_refs": 5000,
    "connect_timeout": 30
  }
}
```

`enabled: false` が既定なので、**設定を書かない限りクライアントはサーバーを探しにいかない**。既存利用者の挙動は一切変わらない。

`auto_start` は `enabled: true` のときにのみ意味を持ち、既定で有効。常駐モードを使うと決めた利用者に、
さらに手動起動を求めないための既定値である（5.1）。プロセスを自分で管理したい場合のみ `false` にする。

## 10. 出力契約の変更

| 変更 | 内容 |
| --- | --- |
| `schema_version` | 1 → 2 |
| 追加 | 全コマンドのエンベロープに `served`（真偽値） |
| 追加 | サーバー経由時のみ、要素に `ref` |
| 追加 | 終了コード 9（`stale_ref`）、11（`server_unavailable`） |

`schema_version` を上げるのは、`served` が全コマンドの出力に現れる変更だから。v2 は v1 の上位互換で、既存キーの削除・改名はしない。skill 文書ではバージョンの等値比較をさせない書き方にする。

## 11. 実装ステップ

### Phase 1: 通信路とサーバー骨格

```text
pyselector/server/transport.py  トランスポート抽象（4.5）
pyselector/server/pipe.py       名前付きパイプ実装（pywin32）
pyselector/server/loopback.py   テスト専用のループバック TCP 実装
pyselector/server/server.py   受付ループ、逐次実行、アイドルタイムアウト、状態ファイル
pyselector/server/client.py   接続とフォールバック判定
serve サブコマンド（--status / --stop / --idle-timeout / --allow-actions）
```

この段階では argv を転送して既存の `main()` を呼ぶだけ。ref はまだ出さない。**ローカル実行と出力が完全一致することをテストで固定する。**

### Phase 2: クライアント統合

```text
--server auto|off|require
設定 server セクション
エンベロープの served と schema_version 2
許可リストとフォールバック
バージョン不一致の検出
```

### Phase 3: ref の公開と利用

```text
サーバー経由時に ref を出力
inspect / act / find / tree の --ref
生存確認と stale_ref
参照表の LRU
```

### Phase 4: ドキュメント

```text
README の常駐モード節
skill 文書（--server require と ref を使う手順、act の追加ゲート）
```

## 12. テスト計画

```text
test_server_protocol.py
  要求・応答の直列化
  argv 転送でローカル実行と同一の stdout / exit_code になること（ループバック TCP 越し）
  許可リスト外のコマンドはサーバーに送らないこと
  バージョン不一致でフォールバックすること

test_server_lifecycle.py
  状態ファイルの書き出しと読み取り
  pid が死んでいる状態ファイルを掃除すること
  アイドルタイムアウトで終了すること（時計を注入）
  --stop で終了すること

test_server_client.py
  --server off はサーバーを探さないこと
  --server auto は接続失敗時にローカル実行すること
  --server require は接続失敗時に終了コード 11 で失敗すること
  --json でないときは auto でサーバーを使わないこと

test_ref.py
  ref の形式とインスタンス ID
  別インスタンスの ref は照会せず stale_ref になること
  LRU で追い出された ref が stale_ref になること
  失効した ref に対して act が操作を実行しないこと
  ローカル実行では ref を出力しないこと

test_server_act_gate.py
  --allow-actions なしで起動したサーバーは act を拒否すること
  設定の act.allow_actions はクライアントの cwd で評価されること
```

サーバーのロジックは 4.5 のループバック TCP トランスポートで、本物のソケット越しに検証する。
名前付きパイプ実装そのものは、実パイプを使う結合テスト 1 本で担保する（ACL が実行ユーザー以外を
弾くことの確認を含む）。

## 13. 受け入れ条件

```text
設定を書かない限り、既存の挙動が一切変わらない
サーバーを起動していなくても全コマンドが従来どおり動く
サーバーを使う場合も、利用者が手動でサーバーを起動する必要がない
テキスト出力（オーバーレイ利用を含む）はサーバーを経由しない
サーバー経由とローカル実行で、同じ argv に対して同じ出力・同じ終了コードになる
find の実行時間が約 0.55 秒短縮される
find が返した ref を act にそのまま渡して、同じ要素を操作できる
失効した ref では act が何も操作せずエラーになる
サーバー未起動時に --server require が終了コード 11 で失敗する
アイドルタイムアウトでサーバーが自ら終了する
パイプが実行ユーザー以外から開けない
--allow-actions なしのサーバーが act を拒否する
```

## 14. リスクと対策

### リスク1: 常駐プロセスが残り続ける

自動起動を既定で有効にした（5.2）ため、利用者が意識しないうちにプロセスが生まれる。

対策: アイドルタイムアウト（既定 300 秒）で自ら終了する。`serve --status` で存在を確認でき、`serve --stop` で明示的に止められる。そもそも `server.enabled` を書かない限り自動起動は起こらないので、常駐を知らない利用者に影響しない。プロセスを自分で管理したい場合は `auto_start: false` を選べる。

### リスク2: 古いサーバーが古い挙動を返し続ける

`pip install -e .` で更新してもサーバーは古いコードのまま動く。

対策: 要求に版数を含め、不一致ならサーバーが拒否 → クライアントはローカルへフォールバックし、標準エラーで通知する。

### リスク3: 失効した ref で意図しない要素を操作する

対策: 使用時の生存確認、インスタンス ID による世代管理、`act` では確認失敗時に操作しない。7.4 のとおり。

### リスク4: サーバー経由とローカルで挙動が食い違う

対策: argv 転送により実行経路を 1 本に保つ（3 章）。Phase 1 で出力一致をテストで固定する。

### リスク5: COM のスレッド制約

対策: 単一スレッドでの逐次処理。UI 操作は元来直列なので実害はない。

### リスク6: 効果が見合わない

短縮は 1 コマンドあたり 0.55 秒で、劇的ではない。

対策: 速度ではなく **ref による対象指定**を主目的として位置づける（1.2）。速度だけが目的なら、この機能は実装しない判断もありうる。

## 15. スコープ外

- MCP サーバー化。本設計の `server/` を土台にすれば後から追加できるが、本計画には含めない
- 複数マシン・リモートからの利用。名前付きパイプはローカル専用とし、本番では TCP を開かない
  （4.1 の認証の議論をやり直すことになるため。テスト専用のループバック実装は 4.5 のとおり）
- 複数クライアントの並列実行。COM の制約から逐次処理とする
- スクリーンショットや画像取得
